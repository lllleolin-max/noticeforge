# Contract and publication

The approval JSON is `noticeforge-approvals/v1` with exactly `format`, nonempty `approved_by`, `roots`, and `components`. Components map each included bom-ref to exactly `artifact` (wheel basename), lowercase `sha256`, `expression`, `choice` (simple license/WITH atoms), and `materials` (all License-File paths mapped to `sha256` and `licenses` atoms). Approval components must equal the root closure. No extra approvals silently broaden it.

The BOM is CycloneDX 1.6 with a positive integer document version. Components are flat application/library records including metadata.component if supplied. Each needs unique bom-ref, name, version, one declared expression and one SHA-256 hash. Dependency rows are explicit, unique and complete, including empty leaves. Dangling edges and duplicate refs are rejected. Diamonds and cycles terminate through visited-node traversal. Nested components, evidence, pedigree, services, compositions, vulnerabilities and formulation are outside this version's scope. Other descriptive fields are retained in the original BOM bytes; they do not modify the declared closure or licensing decisions. No broad full-schema validation claim is made.

PyPA packaging validates and canonicalizes SPDX syntax and the known identifiers. A bounded branch proof validates exactly the human's selected atom union; repeated atoms and WITH exception atoms are preserved. The proof caps intermediate states/products at 4096 rather than expanding an unlimited disjunctive normal form. An exhausted proof refuses input rather than claiming invalidity or legal prohibition. LicenseRef identifies a human-defined license, whose text and attribution still need explicit hashes. DocumentRef cross-document references are not supported by the PyPA grammar.

Each wheel is read into a bounded immutable byte snapshot and hashed before parsing. ZIP entries must have distinct portable paths under NFC plus case folding, no traversal, backslash, special file, encryption, device name or ambiguous trailing dot/space. Name/version/expression must agree with the BOM and approvals. Metadata 2.4–2.6 uses License-File relative to `.dist-info/licenses/`, as defined in PEP 639. A single top-level METADATA is required. An ambiguous legacy License plus License-Expression is refused. All listed files must exist, match the approved hash, have declared license attribution, and collectively cover the selected branch atoms. This does not infer which legal text is sufficient. Metadata and license byte streams are preserved, including line endings and UTF-8 paths. No extractall executes wheel code.

Output component directory names use the full SHA-256 of the original bom-ref, preserving the original ref/name/version and artifact/source/output paths in a structured manifest. Same basenames in different paths or components remain separate. Output contains original BOM/approval bytes, each component's actual METADATA and License-File bytes, NOTICE.txt and manifest.json. Manifest lists every payload's length/hash; its own length/hash is returned separately. The caller can archive this verified directory with its deployment tooling.

All input/approval decisions and resource allowances are checked before a staging directory is created. Each file is exclusively created, flushed and fsynced, then reread against the exact expected bytes. A same-filesystem rename publishes the complete staging directory under a new destination. Filesystem host and output parent are trusted, with no concurrent competing writer, path replacement or hostile symlink changes. Power loss durability of directory entries is not certified, particularly on Windows; normal process interruption before rename leaves no published destination. After rename the complete destination may exist even if the caller was interrupted before receiving the result. There is no automatic retry overwrite.

Bounds are positive integers (booleans refused), with documented finite maxima in `Limits.validate`: individual JSON bytes, component/edge counts, compressed wheel bytes, ZIP member count, each uncompressed member and total uncompressed sizes, total material bytes, and full output bytes including manifest. Actual bounded reads protect compressed inputs; ZIP size declarations bound the material reads, whose CRC is verified by Python zipfile. The tool does not impose a hard wall-clock/CPU bound, authenticate human identities or attest upstream supply-chain provenance.
